## 1. 执行摘要与核心结论

### 1.1 一句话定位

**BiliMind 让技术学习者把 B 站收藏视频转换为可检索、可比较、可追溯、可核对时效性的个人知识库。**

核心问题不是“如何让 AI 总结视频”，而是：**在真实技术学习或开发任务中，用户如何低成本地重新找到、整合并核实过去收藏的知识？**

### 1.2 目标用户、场景和优先级

| 项目 | 建议结论 | 为什么 |
|---|---|---|
| 首批用户 | 经常通过 B 站学习 AI / 编程、已有较多技术类收藏的学生与初级开发者 | 学习任务明确，容易找到用户开展测试 |
| P0 场景 A | 自然语言找回视频中的知识片段 | 需求易理解，能直接测量找回成功率和耗时 |
| P0 场景 B | 跨多个收藏视频比较观点并引用原片 | 更能表现产品差异化与 Agentic RAG 的实际价值 |
| P1 场景 C | 旧教程与当前官方资料的时效性对比 | 有价值但依赖合法联网检索、来源质量和时间信息 |
| 暂不做 | 全平台视频总结、自动学习画像、全自动知识图谱、无限制自主 Agent | 与核心任务距离远，显著增加复杂度 |

**[建议] 第一版主打“双场景闭环”：找回一个片段 + 比较多个视频。** 时效性对比作为展示技术潜力的增强能力，先在少量受控样本中验证。

### 1.3 对现有项目的判断

[原项目自述] 已具备 B 站收藏/视频处理、ASR、SQLite 元数据、ChromaDB 向量检索、DB/Local/Web/Hybrid 自适应规划、多源 Evidence、Claim/Aspect 证据校验、有限 Retry 和 Abstain 等设计；验证方式主要是功能测试和典型案例，原 README 不宣称已有系统性消融实验。

**产品化缺口不是“Agent 不够多”，而是：**

1. 尚没有用户访谈和任务证据证明上述痛点的发生频率与严重程度；
2. 缺少围绕用户任务组织的页面和结果样式，容易把所有问题都做成聊天文本；
3. 知识库覆盖率、ASR 画面盲区、引用失败和授权边界还需要被产品明确告知；
4. 需要以真实任务成功率和系统评测证明 Planner / Verifier 的收益，不能只展示架构图。

## 2. 问题定义：用户到底为什么需要它？

### 2.1 三个待验证的用户问题

| 编号 | 用户任务中的障碍（假设） | 现有做法 | 潜在机会 | 验证信号 |
|---|---|---|---|---|
| H1 | 知道看过某个概念，却忘了具体视频/时间点 | 收藏夹翻找、站内关键词搜索、重新看一遍 | 用语义提问定位原视频片段 | 真实任务找回率、耗时、用户是否复用 |
| H2 | 同一技术的多份教程观点分散，难以整合 | 逐个重看、手工记笔记、复制文本给 LLM | 证据关联的跨视频对比 | 比较任务完整度、来源正确性、节省时间 |
| H3 | 收藏的编程/AI 教程可能因版本变化而过时 | 另查搜索引擎或官方文档 | 历史说法 vs 当前资料 | 版本差异识别准确性、错误采用旧教程的减少 |

这些问题**不能在没有访谈时写成已验证的用户痛点**。尤其要验证：当用户需要知识时，他真的会先去收藏夹找，还是直接重新搜索互联网？这会直接影响产品入口。

### 2.2 Jobs-to-be-Done（JTBD）

> 当我在学习或写代码时遇到问题，隐约记得收藏的视频解释过它，我希望快速找出相关片段，并在必要时比较不同视频的说法，判断哪些结论可信且仍适用，以便继续手头的任务，而不是重新筛查大量视频。

JTBD 对应三个独立子任务：**找证据 → 理解差异 → 做出下一步决定**。其中“下一步决定”可能是回到视频、复核 API、继续追问或保存笔记，并不总是要求 AI 生成长答案。

### 2.3 明确“不解决”的问题

- 不承诺仅凭收藏行为判断用户是否已经学会某知识；
- 不承诺仅凭 ASR 就能理解视频中所有代码、PPT、图表和操作画面；
- 不将视频外的通用常识冒充视频原话；
- 不把“模型给了一个引用”直接等同于“该引用支持该结论”；
- 不假设能够合法、稳定地读取任意用户收藏夹并批量下载全部视频。

## 3. 用户细分与研究计划

### 3.1 目标群体

| 群体 | 典型使用时机 | 最重要的成功结果 | 优先级 |
|---|---|---|---|
| 技术课程学习者 | 课程项目、期末复习、查概念 | 准确找回教程片段 | P0 |
| AI / 软件工程实践者 | 学框架、调代码、比较技术路线 | 跨来源整合与版本核验 | P0 |
| 考研/考证学习者 | 按课程体系系统复习 | 课内知识定位、归纳 | P1 |
| 娱乐视频收藏用户 | 寻找剧情、台词等 | 需求类型差异大 | 暂不覆盖 |

### 3.2 第一轮研究设计（[建议]）

**样本：** 12–15 位受访者，覆盖本科生、研究生与初级开发者；有意识地包含“收藏多但不复习”和“经常复用收藏”的两类用户。优先按照**最近一个月真实行为**筛选，而非笼统的技术兴趣。

**方法：** ① 30 分钟半结构化访谈；② 让用户还原最近一次找知识的过程；③ 现场完成一个自然查找任务；④ 在不预先展示 AI 方案的条件下记录原有方式、耗时与失败点。

**重点访谈问题：**

1. 最近一次收藏技术视频是什么？为什么当时选择收藏而不是记笔记？
2. 最近一次“记得看过却找不到”的例子是什么？最终找到了吗？
3. 实际用的是什么方法：B 站站内搜索、收藏夹翻找、浏览器搜索、笔记软件还是 AI？
4. 什么情况下需要看原视频，什么情况下只需要一句答案？
5. 最近有没有比较过多个讲同一技术的教程？如何判断不同说法？
6. 最近遇到过教程过时的情况吗？如何确认是 API 变化还是自己理解有误？
7. 你的收藏内容中，字幕/语音与画面哪个更重要？
8. 如果 AI 找不到、证据矛盾或需要联网，你希望它如何处理？
9. 你愿意给工具什么数据访问权限？哪些内容不愿上传到外部模型？
10. 请现场展示你上周一次真实的找知识过程。

**分析方法：** 把用户原话/操作记录编码为 `触发任务 → 当前方法 → 遇到阻碍 → 结果代价 → 替代方案 → 发生频率`；同一结论至少可回溯到真实访谈或任务日志。不把 12–15 人样本推断成市场总体比例。

### 3.3 关键证伪条件

- 若大多数目标用户从未复用收藏内容，而主要靠重新搜索，那么“收藏夹优先”的定位需要调整为“当前视频/指定学习清单优先”；
- 若用户只需快速找原片，跨视频整合使用意愿弱，则把“片段找回”作为主场景，跨视频比较作为高级能力；
- 若内容源难以在授权范围内稳定获取，需缩小为用户自主导入的字幕/合法样例，不能绕过权限来维持产品设想；
- 若用户不能区分视频原话与 AI 推断，必须优先改善引用/证据交互，不能先扩功能。

## 4. 竞品与替代方案分析

### 4.1 不是只比较“AI 视频总结器”

用户的真实替代方案包括：B 站收藏夹和站内搜索、浏览器搜索、传统笔记工具、视频 AI 摘要工具，以及通用 AI 资料研究工具。竞品研究应围绕**同一个用户任务**比较，而不仅是功能列表。

| 产品/替代方案 | 可参考的已知能力或使用方式 | 对 BiliMind 的启示 |
|---|---|---|
| B 站原生收藏/搜索 | 收藏与标题/关键词查找 | 需要证明语义找回能更快定位“记得内容、不记得标题”的任务 |
| BibiGPT | [观察] 视频/音频摘要、问答等 AI 能力 | 不能把转写、摘要作为核心差异化 |
| BiliNote | [观察] 转写、视频笔记、部分原片定位体验 | 时间戳、笔记不是独占能力，应做好细节基线 |
| NotebookLM | [观察] 基于用户资料的问答及引用，支持部分在线视频来源 | 来源范围与可溯源交互值得学习，但不等于直接支持 B 站收藏夹 |
| 人工笔记/搜索引擎 | 个性化程度高，但整理和回看需要用户投入 | 价值应体现在真实任务时间与结果质量上 |

**边界：** 此处仅罗列可从公开产品资料确认的一般能力，不声称竞品当前价格、市场份额或性能排名。正式发布竞品表前应重新检查版本和官方文档。

### 4.2 差异化主张与验证

| 差异化主张（[假设]） | 为什么用户在意 | 应怎样证实 |
|---|---|---|
| 收藏夹范围内的语义找回 | 省掉从头翻找收藏夹 | 与用户惯常检索方式比较成功率与时间 |
| 多视频观点的证据级比较 | 避免没有来源的“综合性总结” | 对照人工标准检查观点/引用/遗漏项 |
| 可核对旧教程与当前资料 | 降低照搬过时方法的风险 | 对明确存在版本差异的样本做人工验证 |
| 明确知识覆盖和无法回答的边界 | 用户更清楚系统知道与不知道什么 | 观察用户对结果可靠性的理解和误判 |

**结论：** 真正的差异化是“收藏视频场景中的知识复用闭环”，而不是 LangGraph、Multi-Agent 或单独的 RAG 技术。

## 5. 产品策略与取舍

### 5.1 价值主张

**用户承诺：** “输入一个问题，快速找到你的收藏视频中相关的那一段；需要整合时，让每项观点有出处；需要查新时，清楚区分旧视频与当前资料。”

**产品原则：**

1. **先找依据，后生成解释。** 找视频不必总做长回答；
2. **按任务呈现。** 找回给视频卡片；比较给证据矩阵；查新给时间对照；
3. **来源与权限透明。** 让用户控制本地/联网范围，知道索引覆盖情况；
4. **证据不足可部分回答。** 但不可省略的核心结论缺证据时必须明确拒答；
5. **复杂度由效果决定。** 增加 Agent 节点必须能解释改善了什么、增加了多少成本。

### 5.2 MVP 优先级（决策依据而非具体需求）

| 优先级 | 范围 | 选择原因 |
|---|---|---|
| P0 | 指定内容导入与索引状态、语义找回、时间戳引用、跨视频对比、来源控制、基本反馈 | 形成完整的“收藏 → 查找 → 验证 → 继续学习”闭环 |
| P1 | 历史/当前资料对比、部分回答体验、历史结果/导出 | 提供差异化与复用价值，但不是基础任务必要条件 |
| P2 | 关键帧/OCR/多模态、主动学习规划、知识图谱 | 需先证明具体失败比例与新增成本值得投入 |

**重要取舍：** 推荐先用受控的 10–20 条合规技术视频完成一套好用的场景，而不是先处理上千条收藏并追求“一键全量建库”。

### 5.3 主要产品决策（需记录在 Decision Log）

| ID | 当前建议 | 证据尚缺什么 | 决策复核时点 |
|---|---|---|---|
| D1 | 主场景兼顾片段找回与跨视频比较 | 真实用户任务分布、复用意愿 | 首轮访谈后 |
| D2 | 默认智能来源选择，允许“仅本地”等硬限制 | 来源切换对信任与效率的影响 | 可用性测试后 |
| D3 | 以 ASR/字幕作为 MVP 核心知识源 | 画面独有信息的失败占比 | 首轮 Badcase 分类后 |
| D4 | 保留 Planner 与 Verifier，但须有 Baseline | 对结果、成本、延迟的净收益 | 离线评测后 |
| D5 | 联网用于用户授权的时效性问题 | 不必要联网率、来源质量风险 | Hybrid 实验后 |

## 6. 产品成功标准与指标框架

### 6.1 指标树

**长期北极星候选：每周有效知识复用任务数**。有效任务需要用户确认或独立评测认定其找回/比较/核验目标达成，不能仅以点击或生成回答次数统计。

第一阶段真实用户量有限时，**主指标为标准任务完成率**，以任务耗时作为同等重要的效率指标。

| 层级 | 指标 | 目的 |
|---|---|---|
| 任务价值 | 标准任务完成率、成功任务耗时、回答有用率 | 证明产品相对于原有工作流的价值 |
| 可信度 | 引用定位正确率、关键结论支持率、未回答的关键问题占比 | 证明回答不仅流畅，而且可核实 |
| AI 决策 | 路由合规率、Retriever Recall@5、Verifier 误放行/误拒答率 | 定位 Agent/RAG 的质量瓶颈 |
| 数据可用性 | 合规样本索引成功率、索引覆盖率、ASR 失败率 | 识别知识库本身的盲区 |
| 效率与风险 | P95 延迟、Web 调用率、单位任务成本、权限违规次数 | 约束线上体验与安全边界 |

**[目标]** 不预先编造目标提升百分比。先建立基线，再根据真实任务难度、成本和错误风险制定阶段门槛。各指标的分母、归因规则和事件埋点见 [PRD 第 8 节](./BiliMind_PRD.md#8-指标埋点与评测验收)。

### 6.2 建议的用户实验

至少让 10–20 位测试者完成以下三类任务：

- **找回任务：** 用概念描述找回曾收藏的视频时间片段；
- **比较任务：** 对比 2–3 条教程对同一技术问题的看法；
- **查新任务：** 根据历史教程与当前官方文档判断 API 差异（P1）。

使用同难度任务比较“用户原有找法”与“BiliMind”；交叉安排执行顺序以减少学习效应，统计成功率、耗时、错误来源点击与不确定性理解情况。注意样本较小，报告中应给出人数、题数和实验条件，避免泛化为所有用户。

## 7. 可行性、风险与替代路径

| 风险 | 对用户造成的结果 | 推荐应对 |
|---|---|---|
| B 站账号/收藏内容的授权与平台限制 | 无法合法或稳定建库 | 核查接口权限；优先使用用户授权/合法样例/可导入字幕，不要求用户提交敏感 Cookie |
| ASR 不包含屏幕代码与图片 | 回答缺少关键证据，甚至猜测参数 | 显示数据能力边界；优先原片定位；按 badcase 频率决定多模态投入 |
| 只有部分视频被索引 | 用户误以为“收藏夹没有相关知识” | 显示索引覆盖、处理失败、未支持内容 |
| 联网资料与视频说法矛盾 | 用户错误地把某个版本当成通用事实 | 分列历史/当前及时间；保留冲突与来源 |
| Planner/Verifier 错误 | 错误路由、误拒答、错误放行 | 用人工标注子集、Trace 和消融实验检验 |
| 重检过多 | 延迟、费用和用户流失 | 分场景预算；限制 Retry；优先定向补查 |
| 用户内容和行为泄露 | 信任受损 | 最小必要收集、明确外部模型发送范围、删除机制 |

**备选路径：** 若收藏夹同步难以合法稳定落地，改为“用户主动导入的视频链接/字幕研究工作台”，保持同一核心 JTBD，而不是围绕抓取技术继续扩大范围。

## 8. 研究与产品化里程碑

| 阶段 | 决策问题 | 交付证据 |
|---|---|---|
| 第 1 周：发现 | 真实主场景是找回还是比较？ | 12–15 人研究纪要、假设验证表、竞品任务对照 |
| 第 2 周：体验 | 用户能否理解索引覆盖、引用和联网行为？ | 用户旅程、低保真原型、可用性问题清单 |
| 第 3 周：MVP | 能否完成端到端用户任务？ | 真实视频上的完整演示、异常处理结果 |
| 第 4 周：AI 质量 | Planner / RAG / Verifier 的主要失败点是什么？ | Golden Dataset、Baseline、Trace 仪表盘 |
| 第 5 周：迭代 | 修复是否改善产品结果？ | 2–3 个真实 badcase、消融对比和回归测试 |
| 第 6 周：验证 | 是否比用户原有方法更有效？ | 任务成功率/耗时对照、用户反馈与复盘 |

这不是工作已经完成的声明，而是未来可执行的**产品决策计划**。需求实现与验收定义见 [PRD](./BiliMind_PRD.md)。

## 9. AI 产品经理作品集应该讲出的故事

建议按“**发现问题 → 选择场景 → 设计 AI 策略 → 定义指标 → 分析失败 → 迭代验证**”讲述，技术架构只是其中的设计证据。

面试时最值得回答的四个问题：

1. 为什么用户需要收藏知识库，而不是直接重新搜索？你有什么访谈或任务证据？
2. 什么时候应该返回视频卡片而非一段生成式回答？这怎样影响任务完成率？
3. 为什么 Planner 要在 DB/Local/Web/Hybrid 间选择？相比固定策略增益是否覆盖成本？
4. Verifier 的分数为什么不等于真实准确率？你如何衡量错误放行、误拒答和用户对“未知”的理解？

**简历原则：** “已实现”只写有代码或演示证据的内容；“提升 X%”只写有对照实验、明确样本和计量口径的结果；需求调研人数与真实用户数不能预填。

## 10. 当前仍需回答的开放问题

- 用户会优先搜索收藏夹，还是更需要“当前观看视频”的即时助手？
- 哪些视频/字幕可以在合规条件下被稳定索引，实际可覆盖比例如何？
- 片段找回与跨视频对比哪个更常用、更能产生明确收益？
- 用户希望“自动决定知识源”还是“显式选择仅本地/联网”？
- 有多少关键 badcase 源于字幕缺乏画面信息？
- 加入 Verifier 的收益是否值得增加的延迟与 Token 成本？

这些问题的答案，应决定下一版本的范围，而非预设一个复杂多 Agent 架构后寻找使用场景。
