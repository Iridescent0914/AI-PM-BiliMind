# 对话记录与多轮上下文：后续方向

> 状态：待验证的产品与技术方向，非当前已实现能力；记录于 2026-11-15。

## 当前状态

- 聊天消息保存在当前浏览器的 `localStorage`，按登录会话 ID 区分；刷新页面后可恢复，“清空对话”会删除对应的本地记录。
- 后端数据库目前不保存用户问题或模型回答。换浏览器、换设备，或重新登录得到新会话 ID 后，原记录不会自动出现。
- 前端虽展示历史消息，但提问请求没有把历史消息作为上下文传给模型；**记录可见**与**模型能连续追问**是两个不同能力。

## 产品判断与优先级

当前优先验证“跨收藏夹找回视频和片段 → 生成可核对的笔记”。个人样本阶段，本地保存足以解决刷新丢失问题，服务端聊天记录不是这条核心流程的前置条件。先按 [产品计划](../总体设计/01产品与开发计划.md) 完成任务回放、评测与主要 badcase 修复。

若实际使用或任务观察出现以下需求，再评估数据库持久化：

1. 用户需要在不同设备、浏览器或重新登录后继续查看同一段对话。
2. 用户需要管理多段长期对话，并返回先前生成的笔记或回答。
3. 需要在用户知情的前提下，保留问答与证据以复盘 badcase；固定评测集和人工记录仍可独立开展，不以保存全部聊天为前提。

## 后续分开设计的两项能力

### 1. 有限多轮上下文

先决定产品是否支持“接着刚才的回答追问”。若支持，应让用户明确当前对话范围，并仅传入与追问有关的少量历史消息或摘要；检查旧回答是否会污染当前收藏夹范围、证据引用和拒答判断。此项可以先基于前端保存的消息实现，**不要求先建聊天数据库**。若暂不支持，界面应明确按单轮提问设计。此项对应产品计划的 P1 待办。

### 2. 服务端对话记录

确认跨设备或长期保存确有价值后，再设计按用户归属的对话与消息数据、列表/读取/删除接口、保存期限和清空规则。流式输出需区分进行中、完成与中断，避免把半截回答误当成完整结果。所有读取和删除都要验证用户归属；不得因保存聊天记录而扩大视频检索的数据范围。若要用真实对话做质量分析，先明确告知用户并限制访问范围。

验收时至少检查：同一账号跨设备可恢复、其他账号不可读取、清空后确实删除、流式中断状态准确，以及多轮追问是否仍能正确限定收藏夹和引用来源。

## 暂不实施

本文件只记录方向与触发条件。本轮不新增数据库表、对话 API 或多轮提示词；实施前应根据真实任务和成本重新排优先级。
