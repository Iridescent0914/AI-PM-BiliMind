# Bilibili-RAG 产品与开发计划

> 状态：规划文档。项目当前能力与运行方式以 [README](README.md) 和代码为准；本文件中的待办不代表已经实现。

## 1. 产品主线

**优先目标用户**：收藏技术学习视频的大学生或开发者。首个样本是项目负责人自己，收藏的技术类与知识类视频少于 100 条；这是一项产品定位选择，其他用户是否存在同样需求仍待验证。

**核心任务**：

1. 输入一个主题，跨收藏夹找回相关视频和可跳转片段。
2. 在找到的视频中选择一条或多条，快速得到可复习的单视频笔记或跨视频综合笔记，并能核对关键内容；找回与笔记是同一条优先流程。
3. 当用户明确问“现在是否仍适用”时，对照收藏视频内容与有日期的一手资料。该任务属于后续扩展。

**产品承诺**：候选视频、笔记和回答应说明依据来自哪里；本地视频没有足够依据时，清楚告知用户。网页资料不得被表述为视频中的内容。“全面”指覆盖视频的主要结构、关键论点与必要细节，具体标准需要通过样本视频人工核对；不以堆长文字代替完整性。

**暂不以功能数量衡量成功**。先看用户能否完成上述任务，再决定是否增加 Planner、Verifier、Retry 等环节。

## 2. 统一评测方法

P0 建立一份可重复运行、人工可核对的小型任务集，后续阶段沿用并补充。先从个人收藏中整理 15–20 个有真实依据的问题或笔记任务，再逐步扩充到约 50 个；不能把模型编造的问题写成真实用户需求。任务覆盖：

| 类别 | 示例 | 重点检查 |
| --- | --- | --- |
| 定位片段 | “哪个视频解释了 KV Cache？” | 找对视频与时间段，链接可跳转 |
| 跨收藏夹找回 | “我收藏的哪些视频讨论近期 AI 发展趋势？” | 找到相关收藏视频，不依赖记住收藏夹名称 |
| 单视频笔记 | “把这条视频整理成便于复习的笔记。” | 覆盖视频主线、关键术语和细节，能回到对应片段 |
| 跨视频笔记 | “综合这几条视频对 Agent Memory 的讲法。” | 保留共识与分歧，标明每条观点来自哪条视频 |
| 本地事实问答 | “视频里如何解释 KV Cache？” | 关键结论与原片段一致 |
| 跨视频比较 | “这两条视频对 Agent Memory 的观点有何不同？” | 分别保留各视频观点，不强行合并 |
| 元数据查询 | “我收藏了哪些 Transformer 视频？” | 范围、数量、列表正确 |
| 无证据问题 | “视频是否说过某个未提及的结论？” | 明确证据不足，避免猜测 |
| 时效性问题 | “视频里的 API 现在有什么变化？” | 区分视频内容与当前资料，标明日期与来源 |
| 边界问题 | 未入库、只有标题简介、ASR 错误、选错收藏夹 | 处理方式与提示清楚 |

每个任务至少记录：`输入 / 用户意图 / 指定收藏夹或视频 / 预期证据 / 必须覆盖的内容 / 允许拒答与否 / 实际输出 / 实际来源 / 失败归因`。对笔记任务另外记录应覆盖的视频章节、关键概念、例子、限制与重要遗漏。保留原始输入、检索片段和最终输出，方便复盘。

**核心指标**：连续流程任务完成率、相关片段命中率、笔记关键内容覆盖率、关键结论有证据支持的比例、该拒答时正确拒答的比例。笔记还要记录是否保留不同视频的观点差异，以及用户获得可用笔记所需时间。**护栏指标**：响应时间、单任务模型及 ASR 成本、入库成功率、可跳转来源比例。先测基线，再设阶段目标；不预写“提升 xx%”。自动评判需要抽样与人工标注核对。

Badcase 分类固定为：需求/范围理解、内容获取或转写、索引与检索、路由、证据使用、生成、交互呈现。每次迭代记录问题、假设、改动、同一评测集复测结果，以及时间和成本变化。

## 3. P0：建立可信的现状与基线

**目标**：明确项目已经能做什么、用户最需要什么、当前哪里失败。

  - [x] 明确优先目标人群与当前样本来源。

  - [x] 确认第一版优先体验是“找回相关视频和片段 → 单视频或跨视频笔记”。

## 4. P1：做好找回、笔记与本地问答

**目标**：用户跨收藏夹找到相关视频和片段，选择后获得单视频或跨视频的可复习笔记，并能从笔记和答案回到支持它的原片段；找不到依据时不会误以为模型已经查证。

- [ ] 修正入库状态统计；为视频显示内容来源及可用性：字幕、ASR、AI 摘要、仅标题简介、处理失败。
- [ ] 为检索片段生成稳定的证据 ID，保留视频、分 P、时间范围、内容来源和原文；检查时间戳链接。
- [ ] 先改进检索与上下文组织：指定收藏夹/视频范围、去重、结果数量与长度控制；比较简单检索基线与改进方案。
- [ ] 在界面中串起“候选视频及片段 → 选择视频 → 生成单视频/跨视频笔记”。先验证这个流程是否比直接进入聊天框更符合真实任务。
- [ ] 将现有短摘要作为候选视频的预览，另做完整笔记：单视频笔记按视频结构整理主线、关键概念与解释、步骤或例子、适用条件与限制；跨视频笔记按主题整合共识与分歧，并标明各观点来自哪条视频。关键内容关联可回看的片段。篇幅以覆盖必要内容为准，通过目录与展开/收起控制阅读负担；只有标题简介或低质量文字稿时提示笔记依据不足，不生成看似完整的长文。
- [ ] 让答案中的关键结论引用对应片段；无匹配或仅有弱来源时明确告知，并给出下一步选择。
- [ ] 校验问答与搜索的用户范围，避免跨用户数据混入；处理公开部署所需的凭据保护。
- [ ] 处理前端“看起来能连续追问、实际上未传历史”的落差：支持有限上下文，或在界面明确按单轮提问设计。
- [ ] 用 P0 任务集复测，特别检查找回命中、笔记覆盖与事实性、引用正确性、拒答和获得可用笔记的耗时。

**交付物**：可复现的“找回 → 笔记”演示、本地问答演示、改造前后评测表、典型 badcase 复盘。

**进入 P2 的条件**：本地问答的主要失败不再由入库状态、错误范围或无依据生成造成；用户确有“视频说法与现状比较”的需求。

## 5. P2：按需加入当前资料对比

**目标**：回答涉及时间变化的问题，同时保持视频资料与外部资料的边界。

- [ ] 定义触发规则：仅在用户明确询问当前状况、版本、论文或视频发布后的变化时使用 Web；“视频里怎么讲”仍限定本地证据。
- [ ] 将问题拆为“视频原说法”和“当前情况”两个检索任务；结果附来源 URL、发布日期或更新日期、访问时间。
- [ ] 优先使用可核对的一手资料；无可靠来源时说明无法确认。
- [ ] 在答案中分开展示两类证据，解释差异与可能的时间或版本原因。
- [ ] 与本地问答基线比较：任务完成率、来源质量、误引率、响应时间和成本。

**交付物**：时效性问题的演示、Web 证据记录、前后对照评测。

**进入 P3 的条件**：能指出简单规则无法处理的重复性 badcase，并有评测依据说明新增决策或验证节点值得其成本。

## 6. P3：有条件地增加自适应决策与验证

**目标**：针对已经观察到的失败类型增加必要的决策和反馈环节。

- [ ] 用 P0–P2 的问题分布决定是否需要结构化 Planner；先与规则路由比较，不预设必须用 LangGraph。
- [ ] 对关键结论建立可检查的 claim–evidence 对应；先用离散标签和人工复核，不把未经校准的分数当作可信度。
- [ ] 仅在能补到缺失证据的情况触发一次 Query Rewrite / Retry；对无证据或来源冲突保留明确的无法确认结果。
- [ ] 保存执行轨迹，比较新增节点前后的有效回答、错误拒答、延迟与成本；没有净收益的节点可以删除。

**交付物**：可解释的工作流、节点级 badcase、阶段评测报告，以及对增加复杂度的取舍说明。
