# Bilibili-RAG：早期架构构想（非当前实现）

> 历史设计草案，仅供方案讨论。文中的“当前能力”“已完成”标记和简历表述不代表实际实现。真实状态请以 [项目说明](../README.md) 与 [产品计划](01产品与开发计划.md) 为准。

> 基于自适应检索与证据验证的视频知识库 Agentic RAG 系统  
> **Evidence-Grounded Adaptive Agentic RAG for Video Knowledge Bases**

Bilibili-RAG 是一个面向 B 站视频收藏内容的个人视频知识库问答系统，围绕 **视频内容获取、ASR 转写、结构化元数据管理、向量检索、自适应知识源规划、多源证据融合与答案验证** 构建完整的 Agentic RAG 工作流。

系统不仅回答“视频里讲了什么”，还会根据用户问题动态决定：

- 是否查询 SQLite 中的结构化元数据；
- 是否检索本地视频向量库；
- 是否需要联网补充最新信息；
- 是否同时使用本地视频与 Web 信息；
- 是否需要将复合问题拆分为不同检索 Query；
- 当前证据是否足以支撑生成答案；
- 证据不足时是否需要 Query Rewrite 与二次检索；
- 补充检索后仍缺乏证据时是否主动 Abstain。

项目聚焦视频知识库场景中的三个核心问题：

1. **异构 Query 对知识源和检索策略的需求不同；**
2. **本地视频知识存在缺失与时效性边界；**
3. **检索到相关文本并不等于生成答案一定被证据支持。**

因此系统围绕四个关键能力展开：

```text
Adaptive Retrieval
        +
Multi-source Evidence
        +
Evidence Verification
        +
Iterative Retrieval
```

## 1. Project Overview

Bilibili-RAG 包含从视频知识构建到问答验证的完整链路：

```text
B站登录 / 收藏夹同步
        ↓
视频内容获取
        ↓
ASR 转写
        ↓
文本切块
        ↓
Embedding
        ↓
ChromaDB 向量入库
        ↓
SQLite 元数据管理
        ↓
用户提问
        ↓
Retrieval Planner
        ↓
DB / Local RAG / Web / Hybrid
        ↓
Evidence Fusion
        ↓
Answer Generator
        ↓
Evidence Verifier
        ↓
Pass / Query Rewrite / Retry / Abstain
        ↓
最终答案 + 视频来源 / 时间戳 / Web Citation
```

问答阶段形成一个受控的 Agentic Workflow：

```text
Plan
  ↓

  ↓
Fuse
  ↓

  ↓

  ↓

```

系统的主要模块包括：

```text

Query Decomposition
Unified Evidence Schema
Evidence Fusion
Answer Generator
Evidence Verifier
Query Rewrite
Retry
Abstain
```

项目定位以 **系统设计 + 工程实现** 为主，重点展示 Adaptive Agentic RAG 在真实视频知识库场景中的完整工作流，而不将项目包装为严格实验型研究。

## 2. Why Agentic RAG?

### 2.1 为什么需要 Retrieval Planner

视频知识库中的问题并不适合全部走同一条检索路径。

例如：

- “我的收藏夹里有哪些 Transformer 视频？”更适合查询结构化元数据；
- “视频里怎么解释 KV Cache？”更适合本地向量检索；
- “这个方法 2026 年有没有新的 benchmark？”需要动态 Web 信息；
- “视频里讲的 LangChain API 和现在相比有什么变化？”同时依赖本地视频知识和当前 Web 知识。

因此系统不能只回答：

> “这个问题属于哪一类？”

还需要进一步判断：

```text
这个问题需要什么知识？
        ↓
知识应该从哪里获取？
        ↓
是否存在时效性要求？
        ↓
本地知识是否足够？
        ↓
是否需要拆分 Local Query 与 Web Query？
        ↓
一次检索是否足够？
```

Retrieval Planner 因此承担 **Knowledge Source Planning**：根据 Query Intent、时效性需求、本地知识边界和上下文约束，在 DB、Local RAG、Web 与 Hybrid Retrieval 之间动态规划检索路径。

---

### 2.2 本地视频知识存在 Knowledge Boundary

视频知识库天然具有两个边界：

```text
Knowledge Missing
        +
Knowledge Outdated
```

例如：

> “这个视频里介绍的方法在 2026 年有没有新的 benchmark？”

本地 RAG 最多只能回答视频录制时的内容，无法自然覆盖视频发布后的论文、框架版本和 benchmark 变化。

因此系统采用：

```text
Local-first
    ↓
On-demand Web
```

而不是让所有问题默认联网。

这样既保留本地知识库的准确性和低延迟，也能够在必要时突破本地知识边界。

---

### 2.3 RAG 不等于 Grounded Answer

传统 RAG 通常默认：

```text
Retrieve
   ↓
Generate
```

但即使检索到了相关内容，生成模型仍然可能：

- 过度推断；
- 错误融合多个片段；
- 把弱证据表述为强结论；
- 使用模型参数知识补充没有检索到的信息；
- 忽略 Query 中未被覆盖的子问题；
- 在本地证据与 Web 证据冲突时强行给出单一结论。

因此本项目在 Generator 之后加入独立的 **Evidence Verifier Agent**，显式检查答案和证据之间的一致性。

## 3. System Architecture

整体架构如下：

```text
                         User Query
                             │
                             ▼
                  Retrieval Planner Agent
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
     SQLite Tool       Local RAG Tool      Web Search
   Metadata / DB      ChromaDB / Video      Agent + Tool
          │                  │                  │
          └──────────────────┼──────────────────┘
                             ▼
                       Evidence Fusion
                             │
                             ▼
                      Answer Generator
                             │
                             ▼
                  Evidence Verifier Agent
                             │
                     Evidence sufficient?
                       /              \
                     Yes               No
                      │                 │
                      ▼                 ▼
                 Final Answer      Query Rewrite
                 + Citations           │
                                       ▼
                                  Re-retrieve
                                       │
                                       ▼
                                  Re-generate
                                       │
                                       ▼
                                   Re-verify
                                       │
                          ┌────────────┴────────────┐
                          │                         │
                      sufficient                insufficient
                          │                         │
                          ▼                         ▼
                    Final Answer                 Abstain
```

为了避免 Agent Workflow 无限循环，系统设置：

```python
max_retry = 1
```

即最多进行一次补充检索与重新生成。

这个设计在“具备反馈闭环”和“控制延迟、Token 成本与系统复杂度”之间做了折中。

## 4. Core Design Principles

### 4.1 Agent 负责决策，Tool 负责执行

本项目没有把所有模块都包装成 Agent，而是严格区分：

```text
Agent = Decision / Planning
Tool  = Deterministic Execution
```

当前核心 Agent：

```text
Retrieval Planner Agent
Web Search Agent
Evidence Verifier Agent
```

当前核心 Tool：

```text
SQLite Query Tool
Chroma Search Tool
Embedding Tool
Metadata Filter Tool
Web Search API Tool
ASR Tool
Video Fetch Tool
```

例如：

```text
Web Search Agent
    ↓
决定什么时候搜、搜什么、如何改写 Query、如何筛选结果
    ↓
Web Search API Tool
    ↓
执行真正的联网检索
```

这种边界可以避免“为了 Agent 而 Agent”，也让每个模块的职责更加清晰。

---

## 5. Retrieval Planner Agent

Retrieval Planner 是系统的检索决策核心。

它并不是一个普通分类器，而是执行：

> **Knowledge Source Planning**

### 5.1 输入

Planner 可以接收：

```json
{
  "query": "...",
  "selected_folders": [],
  "selected_videos": [],
  "conversation_context": "...",
  "knowledge_stats": {
    "video_count": 120,
    "indexed_count": 118
  }
}
```

Planner 关注的特征包括：

```text
是否指定收藏夹
是否指定具体视频
是否要求最新信息
是否包含时间词
是否需要列表 / 统计
是否需要跨视频比较
是否包含多个子问题
本地知识是否可能不完整
```

---

### 5.2 输出

Planner 使用结构化输出描述当前问题应该如何检索：

```json
{
  "route": "hybrid",
  "query_type": "freshness_comparison",
  "need_database": false,
  "need_local_vector": true,
  "need_web": true,
  "need_decomposition": true,
  "local_query": "视频中介绍的 Agent Memory 方法是什么",
  "web_query": "latest agent memory methods 2026",
  "reason": "问题同时涉及视频内容与当前发展"
}
```

---

### 5.3 Route

系统支持五类 Route：

```text
direct
db
local_vector
web
hybrid
```

Route 数量保持精简，以避免系统状态空间和 Prompt 逻辑过度膨胀。

---

### 5.4 Knowledge Source Planning

Planner 在一次决策中综合完成：

```text
Intent Analysis
        +
Freshness Analysis
        +
Knowledge Requirement Analysis
        +
Source Selection
        +
Optional Query Decomposition
```

对应执行路径为：

```text
Question
   ↓
Retrieval Planner
   ↓
DB / Local / Web / Hybrid
```

对于复合问题，Planner 还会分别生成 `local_query` 与 `web_query`，使不同知识源接收到更匹配自身语义空间的检索请求。

因此 Planner 的核心职责不是简单 Route Classification，而是：

> 根据 Query Intent、时效性需求和本地知识边界完成 Knowledge Source Planning，并为后续 Retrieval 与 Verification 提供结构化决策。
---

## 6. Query Decomposition

Local RAG 与 Web Search 面向的知识空间不同，因此 Hybrid Retrieval 并不会简单地把同一个 Query 同时丢给两个检索器。

例如：

> “这个视频里的 RAG 方法现在还主流吗？”

Planner 会拆分为：

```text
local_query:
这个视频介绍的 RAG 方法是什么？

web_query:
current mainstream RAG methods 2026
```

然后执行：

```text
Local Retrieval
        +
Web Retrieval
        ↓
Evidence Fusion
```

这样可以减少“同一个 Query 在不同知识源中语义不对齐”的问题。

---

## 7. Web Search Agent

Web Search 主要解决：

```text
Local Knowledge Missing
        +
Local Knowledge Outdated
```

系统不会对所有 Query 默认联网。

### 7.1 触发条件

#### 条件一：Query 明确存在时效性需求

典型关键词：

```text
最新
现在
目前
当前
2026
最新版本
最新论文
最新 benchmark
```

#### 条件二：Planner 判断本地知识明显不足

例如：

> “视频中的方法现在还主流吗？”

这是一个天然跨越“视频历史内容”和“当前信息”的问题。

#### 条件三：Verifier 判定当前 Evidence 不充分

```text
Local Retrieval
      ↓
Generate
      ↓
Verify
      ↓
Insufficient
      ↓
Web Search
```

因此 Web Search 同时可以被 Planner 主动选择，也可以由 Verifier 在反馈阶段触发。

### 7.2 Source Quality Filtering

Web Search 的目标不是“搜到越多越好”，而是尽量保留能够作为 Evidence 的高质量来源。

系统在 Web Evidence 进入 Fusion 前进行基础来源过滤与优先级排序，优先保留：

```text
官方文档 / 官方 Release / 官方仓库
            >
原始论文 / 作者主页 / 一手技术材料
            >
高质量技术博客 / 二手技术解读
            >
普通社区讨论
```

同时结合：

```text
Source Authority
Freshness
Query Relevance
Cross-source Agreement
```

进行结果筛选。

其中需要区分两个概念：

```text
Source Quality
    ≠
Claim Support
```

一个来源本身可靠，并不代表它一定能支撑当前 Answer 中的某个 Claim。

因此系统将两层职责拆开：

```text
Web Search Agent
    ↓
来源过滤、去重、时效性检查
    ↓
Evidence Fusion
    ↓
Evidence Verifier
    ↓
判断 Claim 是否真的被 Evidence 支撑
```

对于涉及框架 API、版本变化、benchmark、论文结论等问题，优先使用官方文档、Release、原始论文或官方仓库等一手来源；普通社区内容主要作为补充信息，而不优先作为关键结论的唯一依据。

系统不试图给整个互联网做“真假判定”，而是将 Source Quality 作为 Evidence 进入验证阶段前的一道质量控制。

## 8. Unified Evidence Schema

Local Evidence 与 Web Evidence 会被转换成统一结构，方便后续 Fusion、Generation 和 Verification。

### 8.1 Video Evidence

```json
{
  "source_type": "video",
  "source_id": "BVxxxx",
  "title": "...",
  "timestamp": "12:34",
  "content": "...",
  "retrieval_score": 0.87,
  "metadata": {
    "folder": "...",
    "author": "..."
  }
}
```

### 8.2 Web Evidence

```json
{
  "source_type": "web",
  "source_id": "https://...",
  "title": "...",
  "date": "2026-xx-xx",
  "content": "...",
  "retrieval_score": 0.83,
  "metadata": {
    "domain": "..."
  }
}
```

通过统一 Evidence Schema，Generator 与 Verifier 不需要分别适配不同检索源。

## 9. Evidence Fusion

Hybrid Retrieval 之后不会直接将所有检索结果粗暴拼接到 Prompt 中。

当前 Evidence Fusion 至少包含以下处理。

### 9.1 Source Tagging

```text
[L1] Local Video
[L2] Local Video
[W1] Web
[W2] Web
```

这样 Generator 可以显式引用不同类型的证据。

---

### 9.2 Deduplication

过滤：

```text
重复视频片段
高度相似的 Web 结果
重复摘要
```

避免同一事实因为重复出现而被模型错误地认为“证据更强”。

---

### 9.3 Source Priority

对于问题：

> “视频里怎么讲？”

优先：

```text
Local > Web
```

对于问题：

> “现在怎么样？”

优先：

```text
Web > Local
```

Source Priority 由 Query Intent 决定，而不是固定全局排序。

---

### 9.4 Conflict Preservation

如果 Local 与 Web Evidence 存在冲突，系统不会强行把两者融合成一个结论。

回答会保留差异：

```text
视频中的说法：
...

当前资料中的说法：
...

二者差异：
...
```

这种“保留冲突而不是消除冲突”的策略特别适合处理：

- 框架 API 更新；
- 方法迭代；
- benchmark 变化；
- 技术路线演进；
- 视频发布后出现的新结论。

---

## 10. Answer Generator

Answer Generator 本身不被设计成独立 Agent。

它的职责保持单一：

```text
User Query
    +
Merged Evidence
    +
Citation IDs
    ↓
Grounded Answer
```

生成约束：

1. 尽可能只基于 Evidence 回答；
2. 关键结论附带 Citation；
3. Local / Web 冲突时显式说明；
4. Evidence 不足时不主动补全；
5. 不把模型参数知识伪装成检索结果。

将 Generator 与 Verifier 拆开，可以避免“Generator 自己生成答案，再自己判断自己是否正确”的自验证问题。

---

## 11. Evidence Verifier Agent

Evidence Verifier 是系统的可靠性控制模块。

它并不评价：

```text
回答是否流畅
回答是否像人写的
回答是否足够详细
```

它重点评价：

> **Answer 中的关键结论是否被当前 Evidence 支撑，以及 Query 的主要信息需求是否已经被覆盖。**

Verifier 的核心不是让 LLM 对整段答案“凭感觉打一个 0～1 分”，而是将验证过程拆成：

```text
Answer
  ↓
Atomic Claim Extraction
  ↓
Claim–Evidence Matching
  ↓
Claim-level Support

Query
  ↓
Aspect Decomposition
  ↓
Aspect Coverage Check
  ↓
Query-level Coverage
```

最后再将这些显式判断聚合成 `support_score`、`coverage_score` 和 Workflow Action。

### 11.1 四项检查

#### Claim Support

Answer 中的关键 Claim 是否能够在 Evidence 中找到直接支持。

例如：

```text
Answer:
“LangGraph 已成为 LangChain Agent 工作流的重要编排方式。”
```

Verifier 会将其视为一个 Atomic Claim，并检查当前 Evidence 是否能够直接支持该结论，而不是仅仅判断检索文本“主题相关”。

#### Evidence Coverage

Query 中的主要信息需求是否都已经有对应证据与回答。

例如 Query：

```text
“视频里的 LangChain Agent API 是什么，
现在有什么变化，
这些变化会不会影响旧代码？”
```

可以拆成三个 Aspect：

```text
A1: 视频中使用的 Agent API
A2: 当前 Agent API 的变化
A3: 变化对旧代码的影响
```

Verifier 分别判断每个 Aspect 是否：

```text
covered
partial
missing
```

#### Source Consistency

检查 Local Evidence、Web Evidence 以及不同 Web Source 之间是否存在关键冲突。

如果冲突可以由时间差、版本差异解释，则保留冲突并在答案中显式说明；如果关键冲突无法解释，则不直接 Pass。

#### Evidence Sufficiency

综合 Claim Support、Query Coverage、关键冲突和缺失信息，判断当前 Evidence 是否足以支撑最终答案。

---

### 11.2 Claim-level Support Scoring

Verifier 首先将 Draft Answer 拆成若干 Atomic Claims。

示例：

```text
C1: Agent API 发生了重构
C2: LangGraph 被用于 Agent Workflow 编排
C3: 某旧 API 已被废弃
```

然后针对每个 Claim 检查 Evidence，并输出离散 Support Label：

```text
full        = 1.0
partial     = 0.5
unsupported = 0.0
```

结构化结果示例：

```json
{
  "claim": "LangGraph 被用于 Agent Workflow 编排",
  "importance": "critical",
  "support": "full",
  "support_value": 1.0,
  "evidence_ids": ["W2", "W4"]
}
```

对于核心结论与补充性结论，可以设置简单重要性权重：

```text
critical claim = 2
normal claim   = 1
```

最终：

```text
support_score
=
Σ(claim_weight_i × support_value_i)
────────────────────────────────────
Σ(claim_weight_i)
```

例如：

```text
C1: critical, full        → 2 × 1.0
C2: critical, full        → 2 × 1.0
C3: normal,   partial     → 1 × 0.5
```

则：

```text
support_score
= (2 + 2 + 0.5) / 5
= 0.90
```

因此 `support_score` 表示：

> **Answer 中已生成的 Claim，有多大比例得到了当前 Evidence 的实际支撑。**

它不是模型对整段答案直接输出的主观“置信度”。

---

### 11.3 Query-level Coverage Scoring

Coverage 检查的是另一件事：

> **用户想问的内容是否被完整覆盖。**

Planner 在复杂 Query 上本身会进行 Query Decomposition；Verifier 可以复用这些子问题作为 `query_aspects`。对于简单 Query，则直接将主问题视为一个 Aspect。

每个 Aspect 的 Coverage Label 为：

```text
covered = 1.0
partial = 0.5
missing = 0.0
```

例如：

```text
A1: 视频中的 Agent API       → covered
A2: 当前 API 的变化          → covered
A3: 对旧代码的影响           → missing
```

则：

```text
coverage_score
= (1.0 + 1.0 + 0.0) / 3
= 0.67
```

因此：

```text
support_score
= “我已经说出来的话，有多少被证据支撑？”

coverage_score
= “用户想知道的内容，我覆盖了多少？”
```

二者必须分开，否则一个“只回答了半个问题但每句话都正确”的答案可能被错误地判定为充分。

---

### 11.4 Evidence Sufficiency Decision

Workflow 不只依赖一个分数阈值，而是采用：

```text
Score Aggregation
        +
Hard Conditions
```

示意规则：

```python
sufficient = (
    support_score >= 0.8
    and coverage_score >= 0.8
    and critical_unsupported_claims == 0
    and unresolved_critical_conflict is False
)
```

其中 `0.8` 是当前系统用于控制 Workflow 的工程经验阈值，不被表述为经过大规模 benchmark calibration 得到的最优阈值。

真正影响 Action 的硬条件包括：

```text
存在 critical unsupported claim
→ Retry

存在主要 missing aspect
→ Retry

问题要求最新信息，但没有有效 Web Evidence
→ Web Search

存在无法解释的关键 Source Conflict
→ Hybrid Re-retrieval / 显式保留冲突

补充检索后仍然 Evidence Insufficient
→ Abstain
```

因此 Verifier 的决策不是简单：

```text
score > threshold → pass
```

而是同时考虑关键 Claim、Missing Aspect、Source Conflict 与检索轮次。

---

### 11.5 Source Quality 与 Verifier 的边界

Verifier 不负责做通用“互联网真假检测”。

Web Search Agent 在检索阶段已经优先保留：

```text
官方文档
官方 Release
官方仓库
原始论文
作者 / 机构一手资料
```

Verifier 重点判断：

```text
这些 Evidence
是否真的支持 Answer 中的 Claim
```

也就是说：

```text
Source Quality
→ 这个来源是否值得进入 Evidence Set

Claim Support
→ 这个 Evidence 是否真的能证明当前 Claim
```

即使一个官方来源本身非常可靠，如果它没有讨论当前 Claim，也不能被计为 `full support`。

---

### 11.6 Verifier 结构化输出

Verifier 的结构化输出不只包含最终分数，还保留 Claim-level 与 Aspect-level 判断，便于 Debug 与 Retry。

示例：

```json
{
  "claim_checks": [
    {
      "claim": "Agent API 发生了重构",
      "importance": "critical",
      "support": "full",
      "support_value": 1.0,
      "evidence_ids": ["W1"]
    },
    {
      "claim": "某旧 API 已完全废弃",
      "importance": "normal",
      "support": "partial",
      "support_value": 0.5,
      "evidence_ids": ["W3"]
    }
  ],
  "aspect_checks": [
    {
      "aspect": "视频中的 API",
      "coverage": "covered"
    },
    {
      "aspect": "当前 API 变化",
      "coverage": "covered"
    },
    {
      "aspect": "对旧代码的影响",
      "coverage": "missing"
    }
  ],
  "support_score": 0.83,
  "coverage_score": 0.67,
  "critical_unsupported_claims": 0,
  "conflict": false,
  "missing_aspects": [
    "对旧代码的影响"
  ],
  "sufficient": false,
  "action": "web_search",
  "rewrite_query": "LangChain current agent API migration backward compatibility"
}
```

Verifier 可以返回：

```text
pass
local_reretrieve
web_search
hybrid_reretrieve
abstain
```

需要强调的是：

> Verifier 是辅助可靠性控制模块，而不是绝对正确的事实 Oracle。

它本身仍可能出现 False Positive 或 False Negative。因此项目将其作用限定为：

```text
发现明显 unsupported generation
识别 missing aspects
检测关键 source conflict
驱动下一轮 retrieval
控制 pass / retry / abstain
```

而不是声称 Verifier 能保证答案绝对正确。

## 12. Iterative Retrieval

传统 RAG：

```text
retrieve once
      ↓
generate once
```

当前系统：

```text
retrieve
   ↓
generate
   ↓
verify
   ↓
sufficient?
   ├─ yes → final
   └─ no
       ↓
    query rewrite
       ↓
    re-retrieve
       ↓
    re-generate
       ↓
     re-verify
```

为了控制系统复杂度：

```python
max_retry = 1
```

如果补充检索后仍然无法得到足够证据，则进入 Abstain。

---

## 13. Query Rewrite

Verifier 不只返回“证据不足”，还可以返回下一轮更明确的 Retrieval Query。

例如第一次：

```text
Agent memory
```

检索结果过于宽泛。

Verifier 可以改写为：

```text
long-term memory implementation in LLM agents
```

然后重新进入 Retrieval。

因此 Query Rewrite 并不是独立堆叠的“第四个 Agent”，而是 Verifier 反馈闭环的一部分。

---

## 14. Abstain Mechanism

如果经历一次补充检索之后 Evidence 仍不足，系统不会继续强行生成。

示例：

```text
当前本地视频与外部检索结果不足以支持该结论。
```

或：

```text
根据当前可获取证据，无法可靠回答该问题。
```

Abstain 机制的目标不是提高回答率，而是降低：

```text
Knowledge Missing
      ↓
LLM Still Answers
      ↓
Unsupported Generation
```

这种风险。

## 15. LangGraph Workflow

系统使用 LangGraph 组织有状态工作流，而不是让多个 Agent 进行自由对话。

State 可以表示为：

```python
class AgentState(TypedDict):
    query: str

    route: str
    query_type: str

    local_query: str
    web_query: str

    db_evidence: list
    local_evidence: list
    web_evidence: list
    merged_evidence: list

    draft_answer: str

    claim_checks: list
    aspect_checks: list
    support_score: float
    coverage_score: float
    critical_unsupported_claims: int
    missing_aspects: list
    conflict: bool
    sufficient: bool

    retry_count: int
    verifier_action: str

    final_answer: str
```

Workflow：

```text
START
  ↓
planner
  ↓
route
  ├─ db
  ├─ local_rag
  ├─ web
  └─ hybrid
  ↓
merge_evidence
  ↓
generate
  ↓
verify
  ↓
sufficient?
  ├─ yes → final
  └─ no
      ↓
 retry_count < 1 ?
      ├─ yes → rewrite / replan → retrieve
      └─ no  → abstain
```

相比自由式 Multi-Agent Conversation，这种图式编排具有几个优势：

- 状态显式；
- 路径可控；
- Retry 次数可限制；
- 更容易 Debug；
- 更容易定位 Planner、Retriever、Generator、Verifier 的 Failure；
- 更适合工程系统而不是 Agent Demo。

## 18. Why Keep SQLite?

系统没有将所有 Query 都统一交给 Vector Search。

原因是很多问题本质上属于结构化 Metadata Query，例如：

```text
收藏夹有哪些视频？
某个 UP 主有多少视频？
某个收藏夹是否包含某类主题？
哪些视频尚未完成索引？
```

这些问题使用 SQLite：

```text
更准确
更快
更稳定
```

因此当前系统实际上同时利用：

```text
Structured Retrieval
        +
Semantic Retrieval
        +
Dynamic Web Retrieval
```

Retrieval Planner 的作用就是根据 Query 选择最合适的知识访问路径。

---

## 19. Why Not Search the Web for Every Query?

全量 Web Search 看起来简单，但会带来：

```text
更高延迟
更多 Token / API 成本
更多噪声
更复杂的 Evidence 冲突
```

同时，大量问题的答案本来就应该以本地视频为准，例如：

> “这个视频里作者是怎么解释 Transformer 的？”

如果默认联网，外部知识反而可能污染原始视频语义。

因此系统采用：

```text
Local-first + On-demand Web
```

仅在以下情况触发 Web 检索：

```text
明确时效性需求
本地知识不足
Verifier 请求补充证据
```

## 20. Why Separate Generator and Verifier?

如果让同一个 Prompt 同时负责：

```text
生成答案
    +
判断答案是否正确
```

容易出现模型“给自己背书”的问题。

拆分之后：

```text
Generator
   ↓
Draft Answer
   ↓
Verifier
   ↓
Answer–Evidence Check
```

可以显式得到：

```text
support_score
coverage_score
missing_aspects
conflict
next_action
```

也更容易定位系统 Failure：

- 是 Planner 选错 Route；
- Retriever 没找到内容；
- Query 太宽泛；
- Generator 过度推断；
- 还是 Evidence 本身就不足。

## 26. Typical Interview Questions

### Q1：为什么需要 Agent，普通 Router 不够吗？

Router 更像固定分类：

```text
query → route
```

Planner 除了分类，还负责：

```text
知识源选择
时效性判断
Query Decomposition
根据 Verifier 反馈重新规划
```

因此 Planner 的核心不是“分类更复杂”，而是从 Routing 上升到 Knowledge Source Planning。

---

### Q2：为什么 Web Search 要做成 Agent？

Web Search API 本身不是 Agent。

Agent 负责：

```text
什么时候搜
搜什么
如何改写 Query
如何筛选结果
```

Search API 只负责真正执行搜索。

---

### Q3：Verifier 会不会判断错？

会。

因此它被定位为：

```text
辅助可靠性控制模块
```

而不是“绝对正确的事实判定器”。

工程上更关注的是：

```text
它能否发现一部分 unsupported generation
它能否给出结构化 missing_aspects
它能否驱动下一轮 retrieval
```

而不是假设 Verifier 永远正确。

---

### Q4：为什么不用所有问题都 Web Search？

因为本地知识已经可以回答大量问题。

全量 Web Search 会增加：

```text
Latency
Token / API Cost
Noise
Source Conflict
```

因此采用 Local-first + On-demand Web。

---

### Q5：为什么不是所有模块都叫 Agent？

因为本项目区分：

```text
Agent = 决策
Tool = 执行
```

例如：

```text
Planner / Verifier = Agent
SQLite / Chroma / Search API = Tool
```

这比把 Retriever、Embedding、数据库访问都包装成 Agent 更符合工程设计。

---

### Q6：到底用的是 LangChain 还是 LangGraph？

两者都用，但职责不同：

```text
LangChain
→ Retriever / Embedding / Prompt / LLM / Tool 等组件

LangGraph
→ State / Conditional Routing / Retry / Agent Workflow
```

因此可以概括为：

> LangChain 负责 RAG 组件能力，LangGraph 负责 Agentic Workflow 编排。

本项目之所以需要 LangGraph，是因为存在 DB / Local / Web / Hybrid 分支、Verifier 反馈、Query Rewrite 和有限 Retry，而不是单一的 `retrieve → generate` Chain。

---

### Q7：Evidence Verifier 的 support_score 是怎么得到的？

不是让 LLM 直接对整段答案主观打分。

流程是：

```text
Draft Answer
    ↓
Atomic Claim Extraction
    ↓
逐 Claim 与 Evidence 对齐
    ↓
full / partial / unsupported
    ↓
按 Claim Importance 聚合
    ↓
support_score
```

映射为：

```text
full        = 1.0
partial     = 0.5
unsupported = 0.0
```

再按 critical / normal Claim 权重聚合。

因此 `support_score` 表示 Answer 中已经生成的关键 Claim 被当前 Evidence 支撑的程度，而不是模型置信度。

---

### Q8：coverage_score 和“证据可信”又是怎么判断的？

`coverage_score` 衡量的是 Query Coverage。

例如用户问题包含三个子问题：

```text
A1 视频中怎么讲
A2 现在怎么讲
A3 两者有什么影响
```

Verifier 分别标记：

```text
covered / partial / missing
```

再聚合为 `coverage_score`。

来源可信度则在 Web Search 阶段先做基础过滤：

```text
官方文档 / Release / 原始论文 / 官方仓库
优先于
二手博客 / 普通社区内容
```

Verifier 不负责判断“整个互联网谁是真的”，而是判断：

> 当前保留下来的 Evidence 是否真的能支撑 Answer 中的具体 Claim。

最终是否 `Pass` 还会联合检查：

```text
support_score
coverage_score
critical unsupported claims
missing aspects
source conflict
retry_count
```

## 27. Project Positioning

Bilibili-RAG 不是追求 Agent 数量的 Multi-Agent Demo，而是围绕视频知识库中的检索决策与答案可靠性设计完整工作流。

项目关注的核心问题是：

> **如何让视频知识库中的 RAG 系统根据 Query 动态选择知识源，并在生成后验证答案是否真的被当前证据支撑？**

系统可以概括为：

```text
Bilibili 视频知识库
        ↓
Retrieval Planner
        ↓
SQLite / Local RAG / Web / Hybrid Retrieval
        ↓
Unified Evidence + Evidence Fusion
        ↓
Answer Generator
        ↓
Evidence Verifier
        ↓
Pass / Query Rewrite / Retry / Abstain
```

其中：

- Retrieval Planner 负责 Knowledge Source Planning；
- SQLite、ChromaDB 与 Web Search Tool 负责不同知识源的实际检索；
- Evidence Fusion 负责统一组织、去重、来源标记和冲突保留；
- Evidence Verifier 负责检查 Claim Support、Coverage、Consistency 与 Sufficiency；
- LangGraph 负责将整个过程编排为有限重试、状态显式的 Agentic Workflow。

## 30. Summary

Bilibili-RAG 是一个面向 B 站视频知识的 Adaptive Agentic RAG 系统，完整覆盖：

```text
视频采集
   ↓
ASR 转写
   ↓
向量与元数据入库
   ↓
Retrieval Planning
   ↓
DB / Local / Web / Hybrid Retrieval
   ↓
Evidence Fusion
   ↓
Grounded Generation
   ↓
Evidence Verification
   ↓
Rewrite / Retry / Abstain
```

项目的核心能力可以概括为：

```text
可规划
可联网
可融合
可验证
可重试
可拒答
```

其关键设计不是堆叠多个 Agent，而是让 **Planner、Retriever、Generator、Verifier 与 Tool** 具有清晰职责边界，并通过 LangGraph 形成一个状态显式、路径可控、具备证据反馈闭环的视频知识库问答系统。
