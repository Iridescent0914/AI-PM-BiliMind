# BiliMind｜把 B 站收藏夹变成可核对的个人视频知识库

> **项目类型：** 受控任务路由 + RAG + 外部服务调用的单工作流产品
> **核心原则：** 先找到用户收藏的依据，再组织答案；结果能回到视频核对。

## 0. 项目一句话定位

**面向收藏了大量技术学习视频、却很难再次找回关键讲解的学生与初级开发者，BiliMind 将 B 站收藏夹转为可语义检索的个人知识库，让用户完成“想起一个知识点 → 找回对应视频/片段 → 获取有来源的解答或笔记草稿 → 跳回原视频确认”的任务闭环。**

它不是把通用聊天模型包装成“懂 B 站的助手”，而是一个**以证据为中心的 Agent/RAG 工作流**：确定性程序负责账号、收藏夹范围和视频数据；语义索引负责从内容中找线索；模型只在明确的任务边界内做路由和表达。产品重点是找回准确性、证据可核对性与可控成本，而非自主 Agent 的角色数量。

## 1. 用户与场景：从“收藏过”到“用得上”

### 1.1 用户是谁、什么时刻需要它

优先面向两类用户。第一类是需要复习算法、AI、编程课程的高校学生；第二类是工作中经常回看框架讲解、技术方案和工具教程的初级开发者。他们的共同特征是：**视频收藏行为已经发生，但知识消费发生在数天或数周之后，用户记得主题，未必记得标题、UP 主或收藏夹位置。**

| 触发时机 | 用户原话示例 | 用户真正需要的结果 | 任务成功的可观察信号 |
| --- | --- | --- | --- |
| 做项目时卡在概念 | “我收藏的哪个视频讲过 KV Cache？” | 找到正确视频，最好落到讲解片段 | 点击来源后能在原视频找到对应讲解 |
| 备考或复习 | “把这两条视频里的 Agent Memory 整理成笔记” | 分清视频观点、有时间依据的笔记草稿 | 能据此复习，并按引用修正内容 |
| 盘点个人资料 | “这个收藏夹里有哪些 Transformer 入门视频？” | 范围正确的视频清单及相关性线索 | 选中目标视频进入下一步观看 |
| 清理收藏夹 | “默认收藏夹里哪些视频适合移到其他文件夹？” | 可预览、可核对的整理建议 | 用户确认后再执行移动操作 |

现有替代方案包括手动翻收藏夹、B 站站内按标题搜索、在笔记软件里二次整理，以及直接问通用大模型。手动翻找的成本随收藏量增长；站内搜索偏向公开视频而非“我收藏过的某个片段”；自己记笔记成本高；通用模型可以解释概念，却无法证明**这条结论来自我收藏的哪条视频**。

### 1.2 用户任务闭环

用户扫码登录并选择收藏夹 → 同步视频关系并构建可用内容索引 → 直接输入模糊主题或明确 BV 号 → 系统识别找回/问答/笔记/清单任务 → 返回候选、答案或草稿以及来源 → 用户点击 BV 视频链接或时间定位链接核对 → 将确认后的内容用于写作、编码或复习。

这里有两个不同的“完成”：**系统完成**是返回结果，**用户完成**是找到能验证的内容并采取下一步动作。产品以后一种作为评测基准。入库后展示的视频摘要、关键要点和实体关系用于快速预览；聊天内指定 BV 号形成的笔记草稿是独立任务，不将预览摘要自动当作完整笔记。

### 1.3 首期范围

围绕个人已授权、已选择的 B 站收藏夹，优先打通“找回—核对—复习”；将广域互联网事实核验、多平台内容聚合以及完全自动的跨系统写入操作放在后续场景验证中。产品以本地使用为主要运行边界，不以公网高并发 SaaS 作为当期承诺。

## 2. 产品目标与成功指标

**业务目标**：证明“收藏资产二次利用”具备明确用户价值，并建立评估新增 AI 调用是否值得的依据。**用户目标**：在不记得标题的情况下快速找到正确视频或片段，生成能够检查来源的笔记。**技术目标**：保证授权范围、内容证据和任务状态可追溯，同时控制调用时间、上下文规模及 ASR 成本。

**北极星指标：可核对知识任务完成率（Verified Task Success Rate，VTSR）**。以已标注期望行为的有效任务为分母，成功找回目标视频/片段、回答要点有直接证据或正确处理边界请求的任务为分子。明确标注为“应拒绝编造”的样本，正确说明证据范围也视为成功；单纯答案流畅不计入成功。

| 过程指标 | 可操作定义与采集点 | 反映什么产品问题 |
| --- | --- | --- |
| 1. 内容就绪率 | 有可用于相应任务的内容证据的视频数 / 已同步视频数；按字幕、ASR、AI 摘要、基础信息四档记录 | 收藏夹同步是否真正变成可查询知识 |
| 2. 视频/片段命中率@3 | 在有人工标注目标的找回题里，前 3 个结果命中正确 BV；单独记录“BV + 时间片段”联合命中 | 找回环节的相关性与定位能力 |
| 3. 关键结论证据支持率 | 人工判定有原文直接支持的关键陈述数 / 答案关键陈述总数 | 引用是否真的在支撑答案 |
| 4. 笔记必备要点覆盖率 | 被正确整理且可溯源的必备要点数 / 人工标注要点数 | 笔记是否只是好看的短摘要 |
| 5. 端到端耗时 | 请求至首字时间、请求至可用结果的 P50/P90；入库耗时单独统计 | 流式反馈能否抵消等待，瓶颈在何处 |
| 6. 单次有效任务成本 | 固定题集的模型、Embedding 增量与 ASR 估算费用总和 / VTSR 成功任务数 | 更多检索、验证或长上下文是否划算 |

**护栏指标**：越权来源数（目标始终为 0）、无证据却给出确定性结论的比例、应拒答题的正确处理率、用户人工补救率以及平均任务交互轮次。人工补救包括手动重问、重新指定 BV、回到收藏夹搜索或放弃任务，需通过计时观察而不是单靠服务日志判定。

采集采用三层口径：接口和日志记录任务类别、状态、耗时与模型用量；评测回放保存返回文本和来源片段；人工按原视频核验 BV、时间戳与结论支持。所有前后比较固定题集版本、收藏夹权限快照、视频索引、Embedding 模型与生成模型，并同时报告有效题数和严重错误数。

## 3. 方案与取舍：为什么是受控 Agent/RAG

### 3.1 三种简单方案各有什么盲点

**仅用规则/数据库**可以给出收藏清单和按标题过滤的结果，却难覆盖“讲过缓存优化但标题没写缓存”这样的语义任务。**仅用语义搜索**可以定位片段，但不适合核对完整收藏清单，也无法很好地把多段内容整理为可复习表达。**仅用通用 LLM**能够生成解释，却无法可靠指出解释来自当前用户的哪个收藏视频。

因此采用“**规则与权限收口 + 任务路由 + 结构化或语义检索 + 有来源的模型生成**”。这属于**单 Agent 式任务编排 / RAG 工作流**，不是多 Agent 自由讨论；“工具调用”首先指后端按任务使用 B 站接口、SQLite、Chroma 和模型服务，不将其等同于模型可无限自主调用外部工具。

### 3.2 三次关键设计收敛

1. **从统一文本检索到按任务分流。** 清单问题的标准答案往往来自收藏夹视频关系，内容解释才需要向量片段。将任务分为找回、笔记和一般问答；明确任务优先采用直接分支，一般问答再选择数据库、向量检索或直接回答。结果是减少不必要的模型规划步骤，同时保留处理自然语言的弹性。
2. **从“有信息就生成”到证据分级。** 字幕与 ASR 可以形成带时间范围的内容片段；B 站 AI 摘要只提供概括性证据；标题、简介通常只支持视频级线索。完整笔记请求以有时间轴的文字稿作为准入条件，避免把标题猜测包装成视频观点。代价是部分视频只能给线索，收益是用户能理解信任边界。
3. **从一次性长稿到有界草稿。** 一次笔记聚焦 1–3 条明确 BV 视频，长稿以有限片段上下文生成并披露覆盖情况。代价是完整性受限；换来时延、Token 成本和遗漏风险的可说明性，也为后续按章节合成留出可评测空间。

| 产品取舍 | 当前策略 | 具体牺牲 | 为什么可以接受 |
| --- | --- | --- | --- |
| 效果 vs 成本 | 高价值内容题走检索和生成；简单清单尽量用结构化数据 | 不让每个问题都走复杂推理 | 用户首先要找对视频，而不是见到最长回答 |
| 轮次 vs 成功率 | 明确的找回/笔记采用短路径；模糊问题允许有限路由判断 | 单轮上下文不能自动理解所有追问 | 先把单任务可核对完成率做实 |
| 自动化 vs 可控性 | 用户选范围、笔记显式指定 BV；收藏夹移动先预览再确认 | 多一次选择/确认 | 避免取错知识或误移动收藏内容 |
| 覆盖 vs 可信度 | 内容来源逐级降级，弱来源只形成线索 | 一些视频只能视频级找回 | 不用伪精确时间戳换表面覆盖率 |
| 召回 vs 安全 | 检索限定当前授权 BV 集合并二次过滤 | 需要额外读取和维护范围关系 | 访问边界优先于多找回一条内容 |

首期优先级按照**能否闭环、是否可核对、是否能用低成本定位问题**排序：先保证授权、内容获取、找回和来源，再做笔记与整理建议；外部事实核验、多轮记忆和自动递归验证以具体 badcase 的收益为进入条件，而不是以“Agent 功能丰富度”为理由堆叠模块。

## 4. 系统架构与关键模块

### 4.1 两条工作流：先构建资产，再完成任务

```text
[用户扫码登录 / 选择收藏夹]
            │
            ├── 入库链路：B 站收藏关系与视频信息
            │             ↓
            │         字幕 → 音频 ASR → B 站 AI 摘要 → 标题/简介
            │             ↓
            │         SQLite：用户会话 / 收藏关系 / 视频缓存 / 整理结果
            │         Chroma：可检索的内容片段与来源元数据
            │             ↓
            │         进度展示 + 内容就绪状态
            │
            └── 任务链路：自然语言 / task / BV / 收藏夹范围
                          ↓
                   会话有效性与授权范围检查
                          ↓
                   任务理解与路径选择
                     ├─ 收藏清单 / 结构化查询 ──→ SQLite
                     ├─ 视频主题 / 内容问答 ────→ Chroma（限定 BV）
                     └─ 指定视频笔记 ────────→ 带时间轴文字稿
                          ↓
                  结果去重 / 来源类型 / 片段时间 / 证据编号
                          ↓
                生成答案或草稿 / 明示证据边界 / 失败兜底
                          ↓
                Next.js 流式展示 + 来源列表
                          ↓
                  用户跳转原视频核对 / 确认使用
```

前端为 Next.js + React + TypeScript；后端为 FastAPI，使用 SQLAlchemy/SQLite 管理会话和视频关系，LangChain/Chroma 存储向量片段，模型和 Embedding 通过兼容 OpenAI 的服务接口调用。环境示例采用 DashScope 兼容接口，音频 ASR 需要可用的转写服务及相应音频处理条件。检索、笔记、问答和片段搜索由聊天接口承担，完整回答与流式回答分别对应 `/chat/ask` 和 `/chat/ask/stream`。

### 4.2 模块职责、失败模式与用户影响

| 模块 | 关键输入 → 输出；依赖 | 典型失败/风险 | 产品处理及其影响 |
| --- | --- | --- | --- |
| 登录与收藏夹选择 | B 站二维码、会话、收藏夹 → 用户可访问视频集合；依赖 B 站与 SQLite | 凭据过期、收藏夹范围选错 | 用会话/收藏夹校验阻断越界，提示重新授权或选择；宁可少答也不跨范围 |
| 内容采集与入库 | 视频列表 → 字幕/ASR/摘要/元数据及任务进度；依赖 B 站、音频与模型服务 | 视频下架、音频不可用、ASR 质量波动 | 按内容源降级并呈现可用信息；区分“同步完成”和“内容可检索” |
| 内容加工与索引 | 可用文字 → 片段、摘要、要点、实体关系与向量；依赖模型与 Chroma | 分块截断、向量索引与视频关系不同步 | 保留 BV/片段来源，按范围过滤；索引准备状态影响回答可靠性 |
| 任务理解/分流 | 问题、显式 `task`、BV → 找回/笔记/一般问答与查询方式 | 清单误走语义搜索、比较题被当单视频问答 | 明确任务走短路径；歧义问题要求说明限定范围 |
| 检索与工具选择 | 查询、允许 BV 集 → 候选视频/片段或数据库清单；依赖 SQLite、Chroma | 召回不准、同视频片段重复、权限外片段混入 | 检索范围前置约束与返回后二次过滤；避免相关不等于可用 |
| 证据组织与生成 | 内容片段、来源类型、时间戳 → 回答/笔记草稿与来源 | 模型过度归纳、来源不能支持结论、长稿覆盖不足 | 保留证据编号与原视频链接，弱证据降级表达，长稿显示部分覆盖 |
| 交互与操作确认 | 流式文本、来源、整理建议 → 可检查结果及用户确认 | 输出中断、用户误以为操作已完成 | 流式改善等待感；整理建议采用预览与执行分离 |
| 状态与可观测性 | 会话、缓存、构建任务、页面消息 → 进度/历史显示/错误记录 | 页面聊天历史与模型真实上下文不一致 | 把连续追问视为新任务并重新指明对象；追踪失败环节而不只记录报错 |

**关键状态边界**：SQLite 记录账号会话、收藏夹关系、视频缓存等持久状态；Chroma 记录面向检索的片段；构建任务独立报告进度；浏览器展示聊天消息，但问答以当次请求为主。因而“已同步”表示收藏夹视频关系已获取，不能等价成“每一条视频都具备高质量字幕与索引”；页面上能看到上条消息，也不等价于模型将其纳入后续推理。

**失败兜底分三层**：采集阶段优先尝试更弱但合法的内容源；查询阶段在无有效内容或越界时说明原因；呈现阶段让用户通过原视频链接自行核对。手动“更新”是可理解的补救入口；自动重试应受频次和费用预算约束，避免将接口故障放大成持续调用。

## 5. 关键技术：解决什么问题、代价是什么

| 技术点 | 产品要解决的问题 | 工作方式 | 代价与体验影响 |
| --- | --- | --- | --- |
| **受控任务路由** | 用户说的是“列清单”“找片段”还是“做笔记” | 显式 task/关键词先进入确定性分支，一般问答再做有限模型路由 | 少量路由误判风险；明确意图时减少无效推理轮次 |
| **工具与参数边界** | 防止把通用生成当作数据访问权限 | 后端调用收藏夹接口、SQLite 查询和 Chroma 检索，校验 session、folder、BV、笔记视频数量 | 校验增加一次数据读取；保证结果属于用户选定范围 |
| **RAG + 向量召回** | 标题未出现的知识点也要找得到 | 对可用视频内容分块、Embedding、Chroma 检索，按用户视频集合约束结果 | 索引构建耗时、Embedding 成本、召回噪声；可找回语义相关片段 |
| **结构化数据与语义数据分工** | 精确清单不应依赖近似语义相似度 | 收藏关系、视频信息用 SQLite；具体讲解用向量片段 | 需要维护两类数据的一致性，但更贴近用户问题性质 |
| **内容源降级** | 字幕覆盖参差不齐 | 字幕 → ASR → 平台 AI 摘要 → 标题/简介；输出保留内容源强度 | 增加采集耗时；弱来源不能支撑细节和准确时间定位 |
| **可追溯证据与时间链接** | 用户必须回原视频核验 | 结果携带 BV、内容来源、可用的时间范围；找回与笔记按本次请求编证据号 `[E1]` 等 | 增加输出元信息，但减少“看似正确、无法复查”的风险 |
| **有界笔记上下文** | 长视频一口气写完成本高、易漏点 | 1–3 条视频、使用有时间轴的字幕/ASR；长稿限制上下文片段预算并说明覆盖 | 节省 Token，笔记是可回查草稿而非逐字完整转录 |
| **流式与状态管理** | 减少等待焦虑并支持任务接续 | `/chat/ask/stream` 推送文本；SQLite 存持久业务状态，前端保留消息显示 | 用户更早得到反馈；对话连续性仍须按单轮语义设计 |
| **预览—确认式操作** | AI 整理建议会改变用户收藏夹 | 默认收藏夹整理先返回建议，再由用户确认移动 | 增加一次确认，但限制误操作的影响面 |
| **坏例驱动的护栏与回归** | 单次回答正确不代表边界可靠 | 用构造的跨范围片段、仅元数据视频与长稿样本验证拒答/范围/覆盖提示 | 需要维护测试样本；把可解释的产品约束转成稳定回归条件 |

因此项目的“Agent 能力”主要表现为**受控决策与工具编排**。会话状态是业务身份与任务状态，不应宣称为跨轮长期语义记忆；B 站内容检索也不同于实时互联网事实搜索。

## 6. 评测设计：40 条离线任务如何打分

评测集以**40 条任务**作为一个可手工复核的版本单位，按照高频 16、长尾 12、边界 8、对抗 4 分布。每类同时含找回、问答、笔记与结构化清单，避免模型只在最擅长的知识问答题里取得高分。配套 `EVAL_SET_TEMPLATE.csv` 给出 10 条可改成真实 BV 的样例。

| 样本类别 | 条数 | 代表问题 | 为什么需要 |
| --- | ---: | --- | --- |
| 高频（40%） | 16 | 模糊主题找回、单视频问答、单视频笔记、收藏清单 | 对应主要产品价值，衡量日常可用性 |
| 长尾（30%） | 12 | 跨视频比较、标题不含关键词、长视频、复合指令 | 暴露语义召回与内容整合的盲点 |
| 边界（20%） | 8 | 仅标题简介、文字稿部分覆盖、无结果、会话过期 | 检查系统是否懂得能力边界 |
| 对抗（10%） | 4 | 未授权 BV、越界收藏夹、伪造时间戳、来源夹带指令 | 检查引用、权限和指令边界 |

**标注字段**：题号、用户原话、前置会话/收藏夹、期望 BV 与片段时间、必备事实或笔记要点、允许的部分回答/澄清/拒答、任务类别、严重度和打分规则。接口回放额外保存原始输出、来源对象、各阶段耗时、Token 与人工复核意见。CSV 为简明入口，扩展字段可以放在回放结果表中。

**人工评分规程**：每题在正确性、完整性、可执行性、安全性、体验五个维度分别记 **0/1/2**：2 = 全部满足标注且证据支持；1 = 部分满足并明确局限；0 = 错误、不可用或模糊遮掩。维度定义如下。

| 维度 | 2 分标准 | 1 分标准 | 0 分标准 |
| --- | --- | --- | --- |
| 正确性 | BV、关键事实与原片段一致 | 只定位视频或事实部分正确且说明范围 | 认错视频或给出错误关键事实 |
| 完整性 | 覆盖全部必备要点/问题子项 | 部分覆盖并标记遗漏风险 | 核心需求未解决却声称完整 |
| 可执行性 | 来源可点击且时间定位有效 | 可到视频但定位需要用户寻找 | 链接失效、伪造时间或无法追查 |
| 安全性 | 仅用授权且可信的来源；正确拒答 | 合规但证据强度表达偏模糊 | 越权、伪造证据、按恶意指令泄露 |
| 体验 | 直接给结论、说明后续核对方式 | 需要少量手动筛选或重述 | 无法理解应做什么或陷入重复步骤 |

**任务成功判定**：五维总分至少 8/10，且正确性、安全性均为 2；应拒答题以“正确说明不可确定的范围”作为正确性基准。关键事实错误、越权结果、虚构 BV/时间戳/引用一票否决。主要报告总体 VTSR，同时单列高严重度错误，防止平均分掩盖灾难性失败。两位评审先独立打分，出现关键维度分歧就回看原视频、保留争议原因；同一任务的评测输入与证据快照固定。

**可复现流程**：① 从真实收藏视频生成题面并人工标注；② 将范围、模型、温度、Top-K、提示词版本与索引版本冻结；③ 回放并保存输入/输出/来源/耗时；④ 人工核对原视频；⑤ 按主失败环节归因；⑥ 每次改动重放同一题集与严重度回归子集。指标按任务类别分桶，避免仅由题集构成变化造成“进步”。

## 7. 对比实验：证据约束是否值得多花 Token

**实验假设**：检索结果不变时，仅优化“交给生成模型的证据组织与引用约束”，可以提高关键结论的可核对性，同时不会因为更谨慎而显著牺牲任务完成率。

**A 基线**：将相同的 Top-K 检索片段拼入普通问答提示，返回解释和视频来源。**B 改进**：使用完全相同的片段集合，仅替换生成阶段的**证据契约模板**——为片段编 `[E#]`，注明字幕/ASR/摘要/元数据的证据等级及时间范围，要求关键结论就近引用、弱来源说清局限、不编造时间戳。这里唯一变化的是生成阶段提示与证据包装规则；检索策略和内容集合不改动。

**固定条件**：40 道成对任务（A、B 各 40 次），相同用户权限、收藏夹快照、模型/温度、Top-K、索引、输入、调用环境；交替执行 AB/BA 减少顺序干扰。逐条记录：task_id、版本、引用片段 ID、原始回答、完成判定、人工核验的关键陈述、首字/总耗时、Token、估算成本与错误类型。

**三个核心指标**：VTSR、关键结论证据支持率、单次有效任务成本。护栏是越权/伪造引用为 0、正确拒答率不下降，及 P90 时延在可接受范围。

下表是**离线实验的示例演算数据，用于说明分析与采纳口径，并非实际用户效果或已核实跑分**。面试提交最终成绩时以同题原始回放为准。

| 对比指标 | A：普通生成 | B：证据契约 | 如何解读 |
| --- | ---: | ---: | --- |
| 可核对任务完成率 | 25/40，约 63% | 29/40，约 73% | 示例改善约 10 个百分点，需按题型检查增益 |
| 关键陈述证据支持率 | 52/74，约 70% | 66/78，约 85% | 示例中直接证据支持的比例提升 |
| 单次请求模型成本 | 约 ¥0.022 | 约 ¥0.026 | 示例增加约 18%，来自证据字段与提示长度 |
| 单次有效任务模型成本 | 约 ¥0.035 | 约 ¥0.036 | 按总请求模型成本 / 成功任务数计算，示例约增 2% |

**结论与决策门槛**：预期提升主要发生在弱来源解释、跨视频比较和笔记引用；简单清单题提升空间小，反而可能因更长提示增加成本。只有当严重错误不增、VTSR 至少不退步、证据支持率有稳定增益，且单次有效成本和 P90 延迟增量可接受，才把 B 作为默认答案路径；若增益集中在笔记与复杂问答，则只给这些任务启用增强证据模板。实验的重点不是展示“生成更长”，而是衡量**多花的 Token 换来了多少可以核对的任务完成**。

## 8. Badcase 归因与一次可复述迭代

坏例按漏斗逐段定位：**意图理解 → 任务规划 → 检索 → 工具选择 → 参数填充 → 执行失败 → 结果组织 → 确认/兜底 → 权限安全 → 成本/延迟**。每条记录保留主因和次因，统计时只把主因计入漏斗；这样修复动作能够落在具体可测环节，而不把所有问题归为“大模型幻觉”。

下表混合了**本地构造边界回归场景**和**同架构的模拟对照风险案例**，便于解释为什么做这些产品护栏；真实任务的最终结论仍依据其原始回放与原视频核对。

| 输入 | 实际表现 / 对照风险 | 出错环节与根因 | 严重度 | 修复动作 | 复测结果 / 验收方式 |
| --- | --- | --- | --- | --- | --- |
| B01：A 用户问“哪个视频讲过向量数据库”，候选混入 B 用户的片段 | 不限制候选范围会产生跨用户来源；属于不可接受结果 | 权限安全；向量相关性不能代替授权判断 | 最高 | 查询前限定会话可访问 BV 集合、输出前再次过滤；越界收藏夹直接拒绝 | 构造的混入片段回归以“返回 A 的来源、越界来源 0 条”为通过条件 |
| B02：给只有标题简介的 `BV_EXAMPLE_C` 写“完整详细笔记” | 元数据容易被模型扩写成不存在的讲解细节 | 证据组织/确认兜底；来源粒度不够 | 高 | 笔记要求字幕或 ASR 时间轴文字稿；提示能提供的视频级线索 | 边界回归检查只返回限制原因及视频线索，不伪造笔记要点 |
| B03：给超长 `BV_EXAMPLE_D` 做“全部内容笔记” | 有界上下文会跳过部分章节，结果容易被误认为全量 | 结果组织/成本延迟；上下文窗口限制 | 高 | 限制上下文片段并显式标注“部分内容笔记草稿”与覆盖比例 | 构造 15 段取 12 段时显示 `12/15` 与局限；继续核对必备要点 |
| B04：“列出当前收藏夹所有 Transformer 视频” | 仅靠向量片段的对照路径，可能漏掉标题匹配但文字稿较弱的视频 | 工具选择；清单数据与内容语义检索混用 | 中 | 清单型查询优先 SQLite 视频/收藏关系，内容型查询用 Chroma | 对照回放按人工清单逐条检查，要求无越界、无虚构并记录遗漏 |
| B05：“这条老视频里的方法现在还适用吗？” | 只看历史视频可能把过去的版本经验写成当前结论 | 意图理解/证据边界；时效性诉求超出本地视频证据 | 高 | 拆成“视频当时说法”和“现时适用性”两个判断，后者提示按日期核查 | 复测标准是只说明可证实的原视频说法，不把旧结论冒充实时查证 |

**优先级机制**：先定义频次 F（同类样本命中数或观察频次）、严重度 S（最高=5、高=3、中=2、低=1）、修复成本 C（工程时间 + 增量调用预算，按 1–5 估计），使用 `P = F × S / C` 比较普通问题的投入产出；越权、伪造引用等最高级安全问题**直接进入 P0**，不等待频次堆积。将高频错误优先做可复现测试，避免“调 prompt 看起来更好”替代验证。

### 一次完整的小迭代：授权范围不等于检索相关性

**发现**：构造两个用户的视频片段放在同一向量召回情境下，语义相似度可能把另一用户的片段排到前面；即便文字回答看起来相关，产品上也属于严重越界。**决策**：不寄希望于模型在答案里自己排除，而把范围作为检索层输入。**改动**：从当前会话与选定收藏夹得出允许的 BV 集合；检索时加范围约束；形成来源列表时再次核验；显式指定无权限收藏夹则在数据访问之前拒绝。**复测**：在混入跨用户片段、指定无权限收藏夹、会话过期三种构造场景中，检查越界来源为 0 且拒绝行为一致。**代价**：每次查询多一次权限/关系检查，且必须关注 SQLite 收藏关系与 Chroma 索引的一致性；但这将模糊的“模型应该安全”转成了确定性的产品验收条件。

另一个迭代示例是长稿笔记：在 15 段构造稿中，只将 12 段送入当前生成上下文时，优先调整**结果命名和覆盖提示**，而不是立刻拉长上下文。因为用户真正风险是把部分草稿当成全量学习资料；是否值得增加多轮分章节生成，需要再用要点覆盖率与单位成本比较。

## 9. 产品亮点与创新点

1. **把“找到一条收藏”定义成可核对任务，而非通用问答。** 用户输入模糊知识点，结果可跳回 BV 视频及可用时间片段；产品价值可以用找回成功和人工核对耗时评价。
2. **“证据等级”进入核心决策。** 字幕/ASR 支撑片段级回答，AI 摘要与标题简介承担视频级线索；笔记有证据准入门槛，降低流畅但无依据的输出。
3. **SQLite 与 Chroma 分工处理不同信息需求。** 收藏清单需要准确的关系数据，讲解内容需要语义召回；通过任务路由选择合适的数据路径，而不是让同一检索模型包办全部问题。
4. **自动化建立在用户可控边界之内。** 选定收藏夹、指定 BV、授权过滤、整理预览确认，让模型负责推荐和整理，不让推荐直接等同于不可撤销操作。
5. **用边界回归管理“看起来很智能”的产品风险。** 对跨范围内容、弱来源笔记和长稿覆盖定义可复测条件，将可追溯性、可信度、成本纳入同一产品迭代讨论。

## 10. 不足、风险与下一步计划

| 等级 | 归属 | 风险与对用户的实际影响 | 下一步迭代与验收 |
| --- | --- | --- | --- |
| P0 | 安全/技术 | B 站登录凭据、用户收藏范围、原始视频内容存储涉及授权与隐私；本地原型边界不能直接按公开服务假设处理 | 梳理会话有效期与凭据保护、最小权限；越界来源 0、越权操作全部阻断后再评估部署形态 |
| P0 | 可信度/产品 | ASR 错字、仅元数据、平台 AI 摘要会让“知道视频讲什么”与“知道视频具体怎么说”混淆 | 明示每条结果的内容来源和可定位粒度；抽检关键结论的直接证据支持率 |
| P1 | 覆盖/体验 | 长稿按有限片段生成草稿，可能遗漏用户最看重的章节；多视频观点归属可能混淆 | 以章节覆盖和观点归属为单位评测，按覆盖率收益决定是否采用分段合成 |
| P1 | 数据/技术 | 视频下架、接口波动、索引与收藏关系变动会造成“同步可见但搜不到” | 区分同步、文字稿、索引状态；按失败阶段提供重新更新入口和错误说明 |
| P1 | 交互/体验 | 页面能看历史消息，但下一次问答主要依靠当轮明确输入 | 对连续追问提供明确重述提示；多轮能力以指代消解题集的净收益决定 |
| P1 | 评测 | 个人技术收藏样本偏窄，人工评审和模拟题可能高估真实效果 | 扩展到不同学科、不同视频来源质量；固定数据快照并保留失败题，做计时任务观察 |
| P2 | 性能/成本 | ASR、Embedding、模型路由与长答案都增加费用和等待 | 以任务维度记录 P50/P90、Token 与有效任务成本；按任务复杂度选择增强检索或证据模板 |
| P2 | 时效性/产品 | 旧视频的观点不能替代当前框架版本或实时网页信息 | 将“原视频说法”与“现时适用性”分开呈现；引入外部核验前先验证用户需求与来源质量 |

**优先顺序**：先守住 P0 的范围与证据可信度 → 形成可信的 40 题离线评测基线 → 根据笔记覆盖与单次有效成本选择章节化笔记、有限追问和按需外部核验。是否引入 Planner、Verifier 或更多 Agent 角色，由 badcase 对任务成功的贡献来决定。

## 11. 三分钟面试讲述版

“我做的项目叫 BiliMind，解决的是一个比较具体的学习场景：用户在 B 站收藏了很多技术视频，但过几周要复习或写代码时，只记得某个知识点，不记得哪条视频讲过，也找不到讲解位置。

所以我的产品目标不是让大模型解释 KV Cache，而是让它告诉用户：**你收藏的哪条视频谈到了它、依据在哪、能不能跳回原片段确认。** 用户先扫码登录，选一个收藏夹，系统同步视频并优先拿字幕；拿不到字幕就尝试 ASR，再根据内容强度降级使用平台摘要或标题简介。SQLite 存收藏关系和视频缓存，Chroma 管可检索片段，前端提供问答和来源跳转。

产品方案上我做了两个关键取舍。第一，没有把所有问题交给一个大 Agent 规划。用户问收藏清单时，结构化数据库更可靠；问具体讲解时走向量检索；明确要笔记时限定 BV 和可用文字稿。第二，我把**证据质量**做成产品约束。有时间轴的字幕可以支撑片段笔记，只有标题简介时只能作为线索。长视频一次生成采用有限片段，结果会写清楚是部分草稿，而不是暗示覆盖了整条视频。

迭代上，一个很典型的 badcase 是检索可能召回其他用户的相似片段。这个问题不能只靠提示词解决，所以我把当前会话允许访问的 BV 集合前置到检索，同时在返回来源前再过滤。构造跨用户、无权限收藏夹、过期会话的回归场景后，就能用‘越界来源为零’判断方案是否守住边界。代价是多一次范围关系检查，但比错误引用更值得。

评测方面，我把任务成功定义成用户能找到并核对内容，设计了 40 条离线题，按高频、长尾、边界和对抗分布；除了成功率还看来源支持、笔记覆盖、耗时和有效任务成本。对比实验只调整生成阶段的证据契约，固定检索和模型，判断额外 Token 是否值得。我的反思是：AI 产品不该用 Agent 数量证明复杂度，而应让用户拿到**有依据、能使用、成本可解释**的结果。”

## 12. 可直接改写进简历的 Bullet

- **场景与闭环：**面向技术学习视频“收藏后难找回”的复习场景，设计 BiliMind 本地知识工作台，串联 B 站扫码授权、收藏夹入库、语义找回、来源片段跳转与笔记草稿，强调结果可回原视频核对。
- **方案与取舍：**采用 FastAPI + SQLite + LangChain/Chroma 的受控 RAG 工作流，区分清单、找回、问答与笔记路径；设计字幕→ASR→平台摘要→元数据的证据分级，单次笔记聚焦 **1–3 条视频**以控制范围与生成成本。
- **评测设计：**规划 **40 条**离线任务评测（高频 16/长尾 12/边界 8/对抗 4），以可核对任务完成率为北极星，同时跟踪片段命中、证据支持、笔记覆盖和单次有效任务成本；设计固定检索条件下的证据约束对比实验。
- **边界迭代：**围绕跨范围片段、弱来源笔记和长视频上下文构造回归场景，采用授权 BV 过滤与证据准入；在 **15 段中抽取 12 段**的测试情境下明确呈现部分覆盖，平衡自动化、可信度和 Token 预算。

### 13.1 关键架构图（文字版）

```text
用户登录 ──→ B 站授权 ──→ 收藏夹/视频元数据 ──→ SQLite
                                           │
                                           └─→ 字幕/ASR/AI摘要/元数据
                                                       │
                                  内容摘要 / 关键要点 / 实体关系 / Chroma 片段索引
                                                       │
提问（task, BV, folder, question） ─→ 会话与范围校验 ─→ 任务路由
                                                          ├→ SQLite 清单
                                                          ├→ Chroma 语义召回
                                                          └→ BV 时间轴笔记片段
                                                                    │
                                               证据去重/编号/强度/时间戳
                                                                    ↓
                                               模型生成与边界说明
                                                                    ↓
                                               流式回答 + 来源跳转 + 用户核对
```

### 13.2 核心指标定义表

| 指标 | 公式 / 统计单位 | 特别注意 |
| --- | --- | --- |
| VTSR | 满足任务成功标准的题数 / 有效任务总数 | 正确拒答可视为成功；严重错误一票否决 |
| 内容就绪率 | 可提供相应任务证据的视频数 / 同步视频数 | 按不同内容来源分层，不把视频关系同步当作内容就绪 |
| 视频命中率@3 | Top3 命中正确 BV 的找回题数 / 有目标 BV 的找回题数 | “命中视频”不等于“命中时间片段” |
| 片段联合命中率@3 | Top3 命中正确 BV 且时间区间相关的题数 / 有目标片段题数 | 无时间轴的来源不进入片段定位分母 |
| 证据支持率 | 有直接原文支持的关键结论数 / 生成的关键结论数 | 主题相关不等于直接支持 |
| 笔记覆盖率 | 已覆盖且归属正确的必备要点数 / 标注必备要点总数 | 对部分草稿同时报告上下文覆盖范围 |
| P50/P90 总耗时 | 请求至可用完整结果的分位数；单位秒 | 单列首字时间和入库耗时 |
| 单次有效任务成本 | 题集总调用成本 / 通过 VTSR 的任务数 | 与单次请求成本区别报告，统一单价与计费单位 |
| 人工补救率 | 需要重问/重选 BV/手动另找的任务数 / 有效任务数 | 需要观察或用户操作记录，不能仅凭模型日志推定 |

### 13.3 评测集字段表

| 字段 | 用途与示例说明 |
| --- | --- |
| `id` | 唯一题号，如 `E01`，贯穿回放和复核 |
| `input` | 用户原话，包含明确 BV 时使用可替换的测试占位符 |
| `expected` | 可人工核验的标准结果；真实回放需要 BV/片段及核心要点标注 |
| `acceptable_alternative` | 合理的部分回答、澄清或拒答条件 |
| `category` | 高频/长尾/边界/对抗，并标出找回、清单、问答、笔记 |
| `severity` | 最高/高/中/低，与优先级和一票否决对齐 |
| `score_rule` | 明确 2/1/0 的判定锚点与严重错误条件 |
| 扩展回放字段 | `folder_ids`, `video_bvids`, `expected_bvids`, `expected_segments`, `must_cover`, `raw_output`, `sources`, `latency_ms`, `token_usage`, `human_review`, `failure_stage` |

同目录文件 [`EVAL_SET_TEMPLATE.csv`](./EVAL_SET_TEMPLATE.csv) 包含 10 条题面和预期行为。正式回放时，BV 占位符需要替换为已获授权、可实际打开的视频，并在扩展回放记录里固定索引版本与收藏夹快照。

### 13.4 Badcase 归因表模板

| 字段 | 记录要求 |
| --- | --- |
